## Project Overview

**BrightSmile Dental Clinic** — a dental practice management SaaS: Next.js 16 frontends and NestJS backends, using Supabase for auth and PostgreSQL via Prisma. **This repository holds the frontends only;** the backends live in `nhabb/BrightsmileClinicBack`.

### Multi-tenancy (organizations → branches) and row-level security
- `organizations` = tenant (one dental business); `branches` = its clinic locations (Beirut, Tyre…). Every tenant table has `organization_id`; location-bound tables (`appointment_slots`, `appointments`, `inventory_items`, plus optional on invoices/expenses/records/documents) have `branch_id`. Each organization has exactly one default branch.
- Tenant context: `TenantContextMiddleware` (`src/shared/tenant/`, registered with `app.use` in `main.ts`) reads the JWT (`org_id`, `branch_id` claims) or, for anonymous requests, the `X-Organization` header / host subdomain / `DEFAULT_ORGANIZATION_SLUG`, and stores it in AsyncLocalStorage.
- Database enforcement: `TenantPool` (a `pg` Pool subclass used by `PrismaService`) runs `SET ROLE dental_app` and `set_config('app.current_org', …)` on every checked-out connection. RLS policies on every table only expose rows of that organization; `app.bypass_rls = on` (superadmin, login/invite lookups via `runAsSystem()`) sees everything. With no tenant, every table reads as empty. The Supabase `postgres` login bypasses RLS, which is why the role switch exists.
- New rows get `organization_id`/`branch_id` from the SQL defaults `app.current_org_id()` / `app.default_branch_id()`, so services rarely set them. Set them explicitly only in scripts that connect as `postgres` (seed).
- `src/shared/prisma/tenant-safety.extension.ts` rewrites `findUnique` to `findFirst` outside transactions: Prisma batches same-tick `findUnique` calls across requests into one statement, which would run under one tenant's RLS settings.
- Prisma queries are lazy: always `await` them *inside* `runWithTenant` / `runAsSystem` (the helpers do this for you when you return the query from the callback). Returning the unawaited query to a caller outside the scope runs it with the caller's tenant.
- Management API: `GET/PATCH /api/organizations/me`, `GET/POST/PATCH/DELETE /api/branches`, superadmin-only `GET/POST /api/organizations`. Platform-only routes use `@Roles('superadmin')` + `RolesGuard`; everything else uses permissions (below). A superadmin passes `X-Organization-Id` (or `X-Organization` slug) to act inside one tenant.
- Requires a session-mode DB connection (direct `:5432` or Supavisor session mode); transaction-mode poolers would drop `SET ROLE` between statements.
- Every checked-out connection also runs `SET idle_in_transaction_session_timeout = '30s'` (`TenantPool.prime`): a client that dies mid-transaction behind Supavisor would otherwise keep its row locks (the invoice-number counter among them) and stall every later invoice of that clinic until the pooler notices; the server now ends such a session itself. If invoices ever hang anyway, look for `idle in transaction` rows in `pg_stat_activity` and terminate them.
- Tests: `npm test` covers the tenancy layer (`src/shared/tenant/*.spec.ts`, `src/shared/prisma/*.spec.ts`, `src/shared/tenancy/*.spec.ts`). `node scripts/smoke-tenancy.js` runs an end-to-end isolation check against a running backend and the real database (creates and removes a throwaway organization).

### Authentication Flow (session cookie)
1. Sign-in: `POST /api/auth/login` (email + password), `/auth/signup`, or Google through Supabase, whose token the callback page trades at `POST /api/auth/provision`. Each answers with the API's own JWT **in an httpOnly cookie**, `bs_session` (SameSite=Lax, Secure in production, 7 days like the token), plus a readable twin `bs_csrf` (`src/shared/common/session-cookie.ts`). The body still carries `token` for API clients.
2. **The browser only talks to its own origin.** The frontend calls `/api/...` on its own domain and `next.config.ts` forwards it to the backend (`API_PROXY_TARGET`, falling back to `NEXT_PUBLIC_API_URL`; nginx does it in Docker), so the cookie is first-party: Safari and Chrome block cookies a different site sets. Never point browser code at the API's own URL again.
3. `requestToken()` reads `Authorization: Bearer` first (Swagger, smoke scripts, other clients) and the cookie second; `JwtAuthGuard` and `TenantContextMiddleware` both use it.
4. **CSRF:** `CsrfGuard` (global) refuses a cookie-authenticated POST/PUT/PATCH/DELETE unless `X-CSRF-Token` equals the `bs_csrf` cookie (code `csrf_failed`). Bearer requests are exempt, since no browser adds that header by itself; `@SkipCsrf()` exempts a route that another site may harmlessly trigger (only `POST /auth/logout`, which is also `@Public` so signing out always works).
5. **Tabs share the cookie.** Each tab keeps display hints (`userRole`, `userId`, `adminUser`, …) in sessionStorage and sends `X-Session-User`; if another tab signed in as someone else, the guard answers 401 `session_user_changed` and `apiFetch` sends the tab to `/login?reason=switched` instead of acting under the wrong name. A new tab of a signed-in browser gets its hints from `/api/auth/me` (`ensureSession()`).
6. Frontend: every call goes through `apiFetch` (`lib/api/client.ts`: same-origin, adds the CSRF and session-user headers); `lib/auth/session.ts` owns `rememberUser`, `ensureSession`, `signOut` (the only way to clear an httpOnly cookie is the API's `POST /auth/logout`). No token is stored in sessionStorage or localStorage any more.
7. Tests: `session-cookie.spec.ts`, `csrf.guard.spec.ts`, `jwt-auth.guard.spec.ts` (cookie cases), `auth-cookies.spec.ts` (the Set-Cookie headers over HTTP).

### Cookie banner and policy (`components/legal/CookieBanner.tsx`, `lib/consent.ts`, `/cookie-policy`)
The banner shows until the visitor chooses and again from any "Cookie settings" link (`openCookieSettings()`; the landing footer has one). "Accept all" and "Essential only" are equally prominent on purpose. The choice is the `bs_cookie_consent` cookie (`{v, at, analytics}`, 6 months; bump `CONSENT_VERSION` to ask again when categories change). Essential cookies need no consent. `analytics` is the only optional category and nothing uses it yet: **anything optional you add must check `hasConsent("analytics")` before it loads, and needs a row in the table on `/cookie-policy`** (which lists every cookie and storage key the app uses). All text is in en/fr/ar under `cookies.*` and `cookiePolicy.*`.

## Working Rules (apply to every change)
- **Review before you finish.** Re-read the diff for correctness, naming and leftovers; fix what you find.
- **Test it.** Run `npx tsc --noEmit`, `npm test` and, for anything touching auth, tenancy or data access, `node scripts/smoke-tenancy.js` and `npm run smoke:permissions` against a running backend. Add unit tests for new logic.
- **Readable, no spaghetti.** Small functions with one job, descriptive names, a short comment explaining *why* where the code is not obvious. No duplicated logic across controllers: shared rules live in one service.
- **Organized in folders.** One concern per folder: `src/shared/tenant` (who the request acts for), `src/shared/access` (ownership rules), `src/shared/common/guards|decorators|filters` (cross-cutting HTTP pieces), `src/shared/tenancy` (organizations/branches API), feature modules under `src/doctor` and `src/patient`. New features get their own `module/controller/service/dto` set.

## API security layers
Every route passes through, in order (see `AppModule`):
1. `JwtAuthGuard` (global): valid token, account active, clinic active. Opt out with `@Public()`.
1b. `CsrfGuard` (global): cookie-authenticated writes carry `X-CSRF-Token` (see Authentication Flow).
2. `RolesGuard` (global): only for platform routes, `@Roles('superadmin')`.
3. `PermissionsGuard` (global): `@RequirePermissions('billing:create')` on a controller or handler; the caller's role must hold every listed permission. No decorator = any signed-in user (then step 4 applies).
4. Ownership: controllers call `AccessControlService` (`assertSelfOrPermission`, `assertPatientProfileAccess(actor, profileId, permission)`, `assertSelf`) so patients only reach their own user, profile, appointments, invoices, records and documents, while staff need the named permission for other people's data.
5. `BranchScopeGuard` (global): staff with `restrict_to_branch` may not name another `branch_id`.
6. Row-level security in PostgreSQL: tenant boundary plus branch scope (`app.branch_scope`), enforced even for raw SQL.
Authorization attributes (role, active flags, branch, the role's permissions) are read from the database per request through `UserAccessService` (60 s cache), so revoking access does not wait for token expiry. Admin endpoint: `PATCH /api/users/:id/assignment` (`role`, `branch_id`, `restrict_to_branch`, `is_active`).

### Money
**One door per document.** Each kind of document is created on the page that owns it, so no screen opens a door into another's work. The **dental chart** (`/admin/patients`, chart tab) is where work is planned **and priced**: each row carries the price it was planned at (`patient_records.quoted_amount`, set on `POST /patient-work` or changed later with `PATCH /patient-work/records/:id/price`). It still creates no money: it issues no invoice and takes no payment, and work already on an invoice shows the price that invoice froze with a lock, and can be neither repriced nor deleted. **The plan is the quote**: see below. The **billing page** (`/admin/billing`) is where every invoice is created (**New bill** → pick the patient → their completed, unbilled chart work is listed to tick, plus any charge that is not chart work, such as a consultation, a product or a missed-appointment fee) and where every payment is received (**Take payment** on any owed invoice), alongside the corrections it already held: refunds, voids and password-confirmed deletion. The **Treatment plans** tab on that same page is the register of every patient plan; `/admin/billing/quotes` is a redirect into it. It does **not** create or edit plans — planning on the chart does. Both builders read `GET /billing/patients/:patientId/billable` (needs `billing:read` **and** `records:read`, since it returns clinical rows), which returns `plan_unbilled`: that patient's plan work, planned or done, carrying no `invoice_id` yet. An invoice line may carry `record_id`: the record is attached to the invoice inside the same transaction (`updateMany ... WHERE invoice_id IS NULL`, rolling back with a 409), so chart work can never be billed twice. The client shape of both documents lives in one place each, `components/billing/invoice-doc.ts` and `quote-doc.ts` (types, normalizers, status colours, aging, the printed invoice/receipt and estimate, and the `PROCEDURES` list the API validates against); the builders are `components/billing/NewInvoiceModal.tsx` and `TakePaymentModal.tsx`, the one payment form in the clinic. The chart links out once, to `/admin/billing?patient=<profile id>`, and an invoice links back to the chart read-only. **A link into the chart fetches the patient it names.** `/admin/patients?patient=<id>` used to look them up in the loaded list, which is one page of twenty, and told the user "That patient is not in your clinic" for everyone further down — false, and alarming. It now falls back to `GET /patients/:id`, mapped by the same `mapPatientRow` the list uses. Who issued an invoice or recorded a payment always comes from the session, never from the request body.

Money received lives only in `invoice_payments`; money paid out only in `expense_payments`. **A payment belongs to the patient, not to an invoice** (`invoice_payments.patient_id`): a treatment plan runs for months, so money regularly arrives before there is a bill to put it on. A `payment_allocations` row is what pays an invoice down, and a payment that is not fully allocated is credit on the patient's account — see **The patient ledger** below. Invoices come from one place, the billing page (`POST /billing/invoices`, which may name the chart records it bills and links them so they cannot be billed twice). The arithmetic every creator follows lives in one place, `src/doctor/billing/invoice-math.ts`: `subtotal` (the lines) minus `discount_amount` (needs `discount_reason`, never above the lines) = `total_amount` (what is owed); an invoice that comes to nothing is `paid` from the start; `due_date` (payment terms) defaults to `procedure_date` (due on receipt) and is never earlier; the creator is the signed-in user, never a body field. Every invoice and quote gets a sequential, gapless, per-clinic-per-year number from a database trigger (`invoice_number` INV-2026-00017, `quote_number` QUO-2026-00004; counters in `document_sequences`, function `app.next_document_number`; migration `20261015120000_billing_numbering_terms_discounts`), so the number is the same whichever screen issued it and a deleted invoice leaves an honest gap. A payment or refund carries `payment_date` (the day the money moved, default today, never in the future); the summary, KPIs and monthly analytics report by that day, not by `created_at`. Outstanding balances age from `due_date` (`GET /billing/aging`: `not_yet_due` is current, then 1-30 / 31-60 / 61-90 / 90+ days overdue; `GET /billing/outstanding` lists each balance with `days_overdue`). **One writer.** Every payment, refund and allocation in the clinic is written by `MoneyService` (`src/doctor/billing/money.service.ts`) and nothing else; `BillingService` and `PatientLedgerService` validate, audit and choose a response shape, but neither creates money itself. It used to be implemented twice, once for "pay this invoice" and once for "take money from this patient", and the two copies disagreed about which row to lock and which number to trust. Three rules it keeps: **the locked invoice row is the truth** (`app.recalc_invoice_totals` maintains `amount_paid` / `remaining_amount` / `status` from an AFTER trigger on `payment_allocations`, so a `SELECT ... FOR UPDATE` on the invoice serialises every allocation touching it and the figures on the held row are authoritative); **the application never writes those totals** (there is no `writeTotals`: the database computed them, so the database is what is read back, which is also why `cancelled` survives a recompute); and **one lock order, invoices ascending by id then payments ascending by id**, which is what stops two desks deadlocking. A refusal from the database is translated by `mapMoneyConstraint` (`money-errors.ts`), so a lost race answers 409 "reload and try again" instead of escaping as a 500; anything unrecognised is re-thrown untouched and stays loud. The three allocation aggregates live once in `money-sums.ts`. Migration `20261009010000_payment_integrity` makes the database enforce it too (positive payment amounts, `amount_paid` within the total with `remaining_amount = total - paid`), and `20261017120000_patient_ledger_allocations` moves the recomputation onto `payment_allocations`: an invoice's `amount_paid` is the sum of its allocations, signed by each payment's `kind`, so a refund allocation subtracts. Money that has moved is never rewritten: corrections are **refunds** (`POST /billing/invoices/:id/refunds`, a row in `invoice_payments` with `kind = refund` and a required reason; the trigger makes `amount_paid` = payments - refunds, so a refund can never exceed what was received) and **voids** (`POST /billing/invoices/:id/void`, status `cancelled` with `cancelled_at`/`cancelled_by` and `cancel_reason`; only when nothing is net-paid, releases the chart records it billed, takes no further payments, excluded from outstanding and from billed totals; migration `20261014200000_quotes_refunds_void`). Deleting an invoice (`DELETE /billing/invoices/:id`, refused if it has any payment or refund row) or a single payment row (`DELETE /billing/payments/:id`) is for pure mistakes: `billing:delete` **and** `ConfirmedAdminGuard` (`src/shared/step-up/`): the caller must be a clinic admin (or a superadmin inside the clinic) and re-enter their own password in the `X-Confirm-Password` header for that request; refusals carry a `code` (`password_confirmation_required` | `password_confirmation_failed` | `password_confirmation_unavailable`). A refund and a void are corrections, so both need `billing:edit`, not `billing:create`. Refunds, voids and deletions are written to `audit_logs` by `AuditService` (`src/shared/audit/`). The billing page prints an invoice (a receipt once paid) with number, terms, discount and money received. Tests: `invoice-math.spec.ts`, `billing.service.spec.ts`, `patient-ledger.service.spec.ts`, `patient-work.service.spec.ts`, `confirmed-admin.guard.spec.ts`; `npm run smoke:billing` (`scripts/smoke-billing.js`) walks plan -> invoice -> payment -> refund -> void, then deposit -> credit -> apply -> refund, against the running API in a throwaway clinic. Work is billed once, enforced twice: the creator attaches records with `updateMany ... WHERE invoice_id IS NULL` (plus `patient_id` and `record_type`, on the same filters its pre-check used) inside the transaction and rolls back with a 409 when the count falls short, and migration `20261015130000_billing_double_billing_guards` adds a trigger that refuses to move a billed `patient_records.invoice_id` to another invoice (releasing it to NULL, what a void does, stays allowed). The record is the unit of protection: there is no quote-level index any more, which is what used to make a plan billed visit by visit unbillable after the first part. "Today" for payment dates, validity dates and aging is the clinic's calendar day (`clinicTodayIso`, `CLINIC_TIMEZONE`, default Asia/Beirut, in `src/shared/common/date-only.ts`), not the server's UTC date; the billing page and the quotes panel use the same zone for their date defaults and limits. The chart routes record work only: they take no price onto an invoice and `created_by` is never a body field anywhere.

### The patient ledger (`src/doctor/billing/patient-ledger.service.ts`)
Money belongs to the patient, because a plan is paid for over months: a deposit when the plan is accepted, more at each visit, and the bills arrive one by one as procedures are completed. `invoice_payments` records that money moved (`patient_id`, `kind` payment | refund); `payment_allocations` records how much of one payment pays down one invoice. One payment can be spread over several invoices and one invoice paid by several payments; **credit** is what is received but not allocated, less refunds taken out of it.

- `GET /billing/patients/:patientId/ledger` — credit on hand, what is still owed, and every payment with the invoices it was applied to.
- `POST /billing/patients/:patientId/payments` (`billing:create`) — take money without naming an invoice. It settles the patient's open invoices oldest due first and keeps the rest as credit; `auto_apply: false` holds all of it.
- `POST /billing/payments/:paymentId/allocations` (`billing:edit`) — put part of an existing payment onto one invoice.
- `DELETE /billing/allocations/:id` (`billing:edit`) — take money back off an invoice and return it to credit. Not a refund: nothing leaves the clinic.
- `POST /billing/patients/:patientId/credit-refunds` (`billing:edit`) — hand unapplied credit back, with a reason (the abandoned plan).

`POST /billing/patients/:patientId/payments` also accepts an optional `invoice_id`: the named bill is filled first and anything beyond it follows `auto_apply` — on to their next oldest bill, or held as credit — rather than being refused for being too much. That is what lets one payment drawer serve both jobs (`components/billing/TakePaymentModal.tsx`: a bill is named, or it is a deposit), and when a bill is named the response carries that `invoice` alongside the ledger so the screen can redraw the row without a second request.

`POST /billing/invoices/:id/payments` still exists and is unchanged for the desk, and now shares the same writer underneath: it refuses an amount above that one bill's balance, which is the difference between it and naming a bill on the route above.

**Two kinds of refund, told apart.** Both are `invoice_payments` rows with `kind = 'refund'`, so `refund_scope` says which: `invoice` (taken back off a named bill; carries an allocation, lowers that invoice's `amount_paid`) or `credit` (unapplied credit handed back; carries no allocation and touches no invoice). `createPaymentRow` takes a discriminated union, so the compiler refuses a refund that does not say which it is. `GET /billing/summary` and `/billing/kpis` report `refunds_on_invoices` and `refunds_of_credit` beside `total_refunded`, which still means both together. Migration `20261018090000_refund_scope`; the backfill rule (an invoice refund is the one carrying an allocation) was checked against `audit_logs` before it ran. The invoice shape returned by every route keeps its `invoice_payments` array — `withAppliedPayments()` flattens each allocation back into a payment row carrying the amount applied *to that invoice* plus the method, day, kind and `created_by` of the payment it came from — so the screens and the printed receipt did not change.

Three invariants the database keeps, not the application (migration `20261017120000_patient_ledger_allocations`): a payment can never be allocated beyond its own amount (`payment_allocations_within_payment`), an allocation can only reach an invoice of the payment's own patient (`payment_allocations_same_patient`), and a cancelled invoice takes no allocations at all. `applyCredit` locks the invoice and then the payment, in the house order, and reads the balance off the locked invoice row — two desks applying the same credit collide on a row instead of both passing their checks. Tests: `patient-ledger.service.spec.ts`, `money.service.spec.ts` (lock order, oldest-due-first settlement against the locked balance, and each database refusal mapping to its answer).

### The plan is the quote (`src/doctor/quotes/plan.service.ts`)

**One living plan per patient, and it is the chart.** The planned and completed rows of `patient_records` *are* the plan; `PlanService.read()` computes the quote from them whenever anyone asks. Nothing is kept in step because nothing is duplicated — the second list of procedures (`quote_items`) and the service that synced it are gone (migrations `20261018120000_plan_is_the_quote_data` and `20261018130000_plan_is_the_quote_drop`).

**A plan can be changed part-way through treatment**, which is the normal case in dentistry and was impossible before: work can be added, repriced or dropped at any point, including after the patient agreed and after some of it has been billed. There is no status machine to get stuck behind — the old `draft -> sent -> accepted -> in_progress -> completed` states, `version`, `supersedes_id`, `valid_until` and the revision flow were all deleted, along with the trigger that moved a quote between them.

**The only thing that freezes is a line on an invoice.** The lock is `patient_records.invoice_id`, not any document's status: once work is billed, its price belongs to that invoice. `repriceRecord` refuses it, the billing claim refuses to re-bill it, and the `patient_records_billed_once` trigger is the backstop. Everything else stays editable, and a billed line stays *visible* in the plan with the price the invoice froze — the plan total covers the whole course of treatment, not just what is left. **The freeze explains itself.** On the chart a billed price is a focusable button, not a dead span: clicking it names the bill that froze it, says why a bill’s lines cannot change once issued, and gives the only correction there is — cancel that bill and reissue, refunding anything received first. It had been relying on a hover `title`, which is invisible on a touch screen and to a keyboard, and `invoice_number` was never selected into the chart at all, so the row could only ever say "billed". `repriceRecord`’s refusal names the bill and the way forward too, for any caller that reaches it.

- `PLAN_RECORD_TYPES` (`plan-record-types.ts`, a leaf module both quotes and billing import) is the single definition of what counts as plan work: `treatment_plan` and `treatment`. A `missing_tooth` is a finding, not work, and clinical notes are never priced — so neither can inflate an estimate.
- A line with no price is reported as `totals.unpriced_count` and rendered "not priced", **never summed as 0**: a never-priced row must not quietly shrink the plan total.
- The chart carries its own plan: `GET /patient-work/chart/:patientId` returns `plan`, so the teeth and the estimate are computed from the same rows and cannot disagree, and the screen needs one request.

**What a patient was handed is a separate, append-only record.** `quote_sends` stores the total and the lines as they stood each time **Give to patient** was pressed (`POST /quotes/:id/send`). It has `SELECT, INSERT` for `dental_app` and deliberately no `UPDATE`/`DELETE` — a dispute record that can be edited afterwards is not a record. This is what answers "you told me 1,400" once the living plan has moved on; the doctor never manages versions. Its price columns are named `quoted_total` / `quoted_lines` on purpose: the assistant hides price fields **by column name**, so a column called `total` would have blanked unrelated fields elsewhere.

Routes (`quotes.controller.ts`): `GET /quotes` (every patient's plan), `GET /quotes/patients/:patientId`, `GET /quotes/:id`, `POST /quotes/:id/send`, `POST /quotes/:id/accept` (a dated fact that gates nothing, and records WHAT was agreed to — see below), `PATCH /quotes/:id/notes`. Nothing here creates or edits plan lines — that is `/patient-work`, because planning work is a clinical act. UI: `components/chart/PlanQuoteBand.tsx` on the chart, `components/billing/QuotesPanel.tsx` as the clinic-wide register (the Plans tab of the billing page — a list only; opening a row opens that patient’s money file), `components/billing/quote-doc.ts` for the shared shape and the printed plan. Tests: `npm run smoke:plan-quote` walks plan → send → agree → **add work after agreeing** → bill one line → billed line frozen while the rest stays repriceable → two sendings with two totals.

**Billing reads one flat list.** `GET /billing/patients/:patientId/billable` returns `plan_unbilled`: every plan row with no `invoice_id`, each tagged `planned` or `done`. Both are billable — paying for a crown before it is cut is ordinary — and the chart's price is the price, because there is no second store to reconcile. `treatment_invoices.quote_id` and the `one_live_per_quote` index are gone with it: that index was the precise reason a plan billed visit by visit had to leave the link empty, and the per-record guard is strictly stronger.

### Two money screens, one for each act (`/admin/billing`, `/admin/payments`)

**Billing is where a bill is made; Payments is where money is received.** They are different acts, often by different people minutes apart, so each has its own door in the sidebar. Billing carries the two registers of documents — **Bills** and **Treatment plans**. Payments is the desk’s till: **Owed** (every unpaid bill, longest overdue first, each with Take payment) and **Taken** (every payment and refund in a chosen window, with who paid, how, which bills it reached and who took it), over a strip of Taken / Unpaid / Overdue and a per-method split for counting the drawer.

**Each page does one kind of act.** Billing makes bills and corrects them — void, delete, refund, print — and acts on plans; it offers no way to take money anywhere, not on a bill row, not in the bill detail, and not in the money file it opens. Issuing a bill no longer hands back a payment form: it says so in a toast whose action carries the desk to `/admin/payments?patient=<id>`. Payments receives money and moves money already received (credit onto a bill, an allocation undone, credit handed back), and never makes a bill.

**Splitting the screens did not split the doors.** `TakePaymentModal` is still the only payment form in the clinic and `PatientDrawer` still the only patient money file; the drawer is read-only about money unless the page that opened it says otherwise. `allowMoneyActs` and `allowPlanActs` are how a page grants what it is for — Payments passes the first, Billing the second — so the same file shows the same history from both and only acts where the act belongs.

Every figure on both pages comes from the server: the till headline and its method split are `GET /billing/summary` (`total_income` and `by_method`, which `moneyMovedByMethod` derives with the same sign rule, so the parts add to the whole), and Unpaid / Overdue are `GET /billing/kpis`. Summing the loaded rows instead would be a second definition of a figure that already has one. `GET /billing/invoice-payments` grew from bare ids for charts into the list a person reads, and takes `from` / `to` / `method`, windowed on `payment_date` like every other report.

### The agreement is for a plan, not for a patient (`src/doctor/quotes/plan-digest.ts`)

A plan stays editable to the end of treatment, so an agreement taken in October can outlive the plan it was given for: adding work left `accepted_at` stamped and the chart still reading "Agreed 17 Oct" for a plan that had grown since. `accept()` now also stores `quotes.accepted_digest`, a fingerprint of **what** was agreed to, and `PlanService.read()` returns `agreement_stale` when the plan no longer matches it. The desk is told, in the band and in the money file, to give the patient the new plan and take the agreement again; `accepted_at` is kept, because when they first agreed is still a fact.

**The fingerprint covers the deal, never the progress.** Each line’s procedure, tooth and price are in it; its state, dates, invoice and payments are deliberately not. Get that wrong in either direction and the feature is worse than nothing — too loose and a changed plan still reads as agreed, too tight and finishing a filling demands a fresh signature. `plan-digest.spec.ts` pins both directions and `smoke:plan-quote` asserts that billing a line does **not** make the agreement stale.

It is an opaque hex digest and deliberately **not** a price column, so it needs no `pricing:read` gate, no entry in `PRICING_COLUMNS` and no view in schema `agent`; `quotes` is granted at table level, so the column needed no grant either (migration `20261018140000_plan_agreement_digest`, re-runnable). An agreement taken before the column existed has `accepted_digest` NULL and is reported as not stale: better than nagging about a change nobody can show, and the next agreement taken makes the question answerable.

### One money truth: a chart figure is not a money figure (`src/doctor/billing/money-figures.ts`)

**A chart figure is what the work is worth. A money figure is what an invoice says.** They live under different keys, are named differently, and are never compared. Chart-side figures end in `_value` and sit under `plan_figures` / the plan's own `totals`; money-side figures are bare nouns under `figures` and are only ever sums of invoice or payment rows. `billed_value` (what the chart priced the billed work at) and `billed` (what those invoices came to, after discounts, plus any charge that was never chart work) are different numbers by construction — the names say which world each lives in.

`money-figures.ts` is the only definition of each money figure, and the layer above `money-sums.ts` (which owns the allocation aggregates and whose SQL aliases the specs match on; `money-figures` imports it, never the reverse). It exports `OWED_INVOICES` — **the** outstanding predicate, `LIVE_STATUSES` plus `remaining_amount > 0`, which replaced five hand-written variants with two different meanings — and `BILLED_INVOICES`, plus `patientMoneyFigures` / `clinicMoneyFigures` / `figuresFromRows`, which every reader now goes through: `getSummary`, `getKpis`, `getOutstandingPayments`, `getAgingReport`, `getPatientFinancials`, `ledger()` and `statement()`. Two identities hold over every figure set and are asserted by the specs and both smokes: `received = applied + credit_held` and `billed - applied = due_now`. `patientMoneyFigures` batches its reads in one **interactive** `$transaction` (never the array form — see `no-batch-transactions.spec.ts`) so the identities cannot be caught mid-write. Round once, at the `MoneyFigures` boundary, never inside the sums.

Two renames came with it. `getPatientFinancials.total_paid` became **`total_applied`** (it was allocated money only, so a patient who had just paid a deposit read as having paid nothing) and gained `total_received` + `credit_held`; the field is agent-visible, so `get_patient_financials`'s tool description describes all of them. `isNotYetDue` (`invoice-math.ts`) exists so `getAgingReport` has no date source of its own: it used to derive `todayStart` from the server's UTC date while calling `daysOverdue` on the clinic's calendar, two answers to one question a few hours apart each night.

### The patient statement (`GET /billing/patients/:patientId/statement`)

The document a patient and an accountant both ask for, composed from the plan and the ledger with no storage of its own. It answers in two blocks that cannot be confused. `figures` is the money side — `billed`, `received`, `applied`, `credit_held`, `due_now`, `overdue` — every member straight from `money-figures.ts`, so a patient's figures are the clinic's figures narrowed to them and `billed - paid = unpaid` holds by construction. `plan_figures` is the chart side — `plan_value`, `billed_value`, `unbilled_value`, `unpriced_lines` — what the course of treatment is worth at the chart's prices. **Due now** (bills issued and unpaid, what the desk chases) and **Not yet billed** (work with no bill, what the patient still faces) are different questions and a screen that answers only one of them misleads somebody. `figures.plan_total` / `.remaining_on_plan` / `.unpriced_lines` survive as deprecated aliases for one release only.

### The plan says how far the money got

A plan line's state is the chain **planned → done → billed → part paid → paid** (`PLAN_LINE_STATES`, `planLineState()` in `plan-record-types.ts`), and the last two come from the line's invoice, carried on the join `PlanService.read()` already makes. Before this a line said `billed` and stopped there, however much of that bill had been paid, so the chart could never show what had actually been collected.

**There is deliberately no per-line paid amount, and no `paid` column on `patient_records`.** Money is allocated to an invoice; there is no edge from an allocation to a line, `invoice_line_items` has no `record_id`, discounts are invoice-level and invoices carry charges that were never chart work. Any pro-rata figure would be a fifth definition of "paid" printed next to a real price — and a stored one would be a second store of money to keep in step, which is exactly what `BILLING_REVAMP.md` Part B deleted. The honest version needs no migration at all.

`locked` stays separate from `state`: it is the freeze rule that `repriceRecord`, the billing claim and the `patient_records_billed_once` trigger all enforce, and a display enum must not become the authorization predicate. **Widening the chain left `=== 'billed'` compiling and silently wrong** for a line that had since been paid — every "is this frozen?" test is `locked` or `isBilledState(state)`, and only display code may name a state. The plan's `totals.billed` was renamed `billed_value`, `unbilled_value` was added, `counts.billed` keeps meaning "on a bill" with `part_paid` / `paid` as subsets of it, and `settlement` reports what this plan's work turned into over its **distinct** invoices (two lines on one bill must not count it twice). `settlement` covers only the invoices this plan produced, which is a subset of the patient's, so it is not their balance — the statement is.

The client mirrors all of it from one module, `client-app/frontend/components/billing/money-words.ts`: `MONEY_WORD` (the English strings the print helpers read), `MONEY_KEY` (the `money.*` i18n keys the screens read, present in en/fr/ar), `PLAN_STATE_LABEL` / `PLAN_STATE_TONE` and `INVOICE_STATUS_TONE` / `INVOICE_STATUS_LABEL`. One word per concept — **Plan total, Not yet billed, Billed, Paid, Unpaid, Credit on account, Bill total** — replacing six names for an unpaid balance (Remaining / Owed / Still owed / Due now / Outstanding / Balance due) and four for what was invoiced. Paid and Unpaid are used of one bill, one patient and the whole clinic; the scope is said by where they sit, and the billing page's clinic strip says it out loud with an **Across the clinic** eyebrow.

### One screen for a patient's money (`client-app/frontend`)

**The billing page is the hub and the patient drawer is the file.** `/admin/billing` carries two registers as tabs — **Bills** and **Treatment plans** — over one clinic strip headed **Across the clinic**, whose four figures come from `GET /billing/kpis` rather than from a sum of the page of invoices that happened to be loaded (a clinic with more bills than the page fetched used to show a wrong total under a confident label). A row in either register opens `components/billing/PatientDrawer.tsx`.

The drawer is the only place a patient's money is read or acted on. It replaced two dialogs that opened from the same row and listed the same payments — a read-only history and an "account" that could move credit — which read `/statement` and `/ledger` for the same balance and called it "Due now" in one and "Still owed" in the other. **`GET /billing/patients/:id/ledger` is now called by no screen**: `credit_balance` is `figures.credit_held`, `outstanding_balance` is `figures.due_now`, and the open bills come from the invoice list the drawer already has. It opens on the chain **Plan total → Billed → Paid**, each stage carrying what leaks from it (work not yet billed, bills still unpaid) as a badge, with credit on account outside the chain because it is not a stage. Under that, four tabs: Timeline, Bills, Payments (which carries applying credit to a bill, undoing an allocation and handing credit back, with the reason asked for in a dialog since it lands in `audit_logs`) and Treatment plan (which carries Give to patient, Patient agreed and Print). It is a `Drawer`, not a `Modal`, so the register stays visible behind it and the payment form, the bill builder and the password prompt stack over it as proper centred dialogs.

**One payment form.** `TakePaymentModal` takes a payment against a named bill or, with `patient` and `open` instead, a deposit with no bill named. The second form inside the old account dialog — same endpoint, different layout, different `auto_apply` default — is gone.

**What the address bar may say** (`/admin/billing`): `view=bills|plans` picks the register, `patient=<id>` opens that patient's money file, and `patient=<id>&new=bill` opens the builder, which is what `?patient=` alone used to do. The query is read inside an effect, never in a lazy initial state — this page is server-rendered first, so an initializer would run where there is no window and hydration would keep that empty answer.

**The chart keeps the clinical story and computes no money.** `PlanQuoteBand` renders **Plan total · Billed · Not yet billed** straight off `plan.totals`, so the chart has exactly one arithmetic source (`GET /patient-work/chart/:patientId`) and the drawer exactly one (`/statement`); neither re-derives the other's numbers. It keeps the three plan acts and the sent history, and links out once — **Money file** → `/admin/billing?patient=<id>`. The drawer is deliberately not mounted on the chart: its footer is Take payment and New bill, and the chart does not create money.

### Receipts, refunds, VAT and expenses (the owner's money model, 2026-10-20)

**Every money document has a number** made by the database, never by the app: `<PREFIX><YY>-<NNNNN>`, one counter per clinic, kind and year, starting at 00001 each January and never reused (`app.next_document_number`, migration `20261020100000_document_numbers_iv_rt_rf_ex`). **IV** invoice (`treatment_invoices.invoice_number`), **RT** receipt and **RF** refund (`invoice_payments.document_number`, by `kind`), **EX** expense (`expenses.expense_number`). Rows created before the migration keep their old `INV-YYYY-NNNNN` invoice numbers; the owner treats that data as test data. `document-numbers.spec.ts` pins the format and prefixes.

**Every payment is a receipt (RT).** "Take payment" on an invoice makes a receipt and applies it in one step (`POST /billing/patients/:id/payments` with `invoice_id`, `auto_apply: false`: anything beyond the bill stays open on the receipt, never on another bill unasked). "New receipt" is a deposit, a receipt with no invoice yet (`POST /billing/receipts`, `billing:create`, optional `reason` kept in `notes`). An invoice can be paid out of an open receipt with `POST /billing/payments/:id/allocations` ("Pay from a deposit" in `TakePaymentModal`). A receipt's figures and status are computed, never stored (`receipt-math.ts`): `held = amount - applied - refunded`, status `open | partly_used | used | partly_refunded | refunded`. `GET /billing/receipts` (filters `patient_id`, `kind`, `status`, `from`, `to`, `method`) feeds the Payments page's Receipts tab.

**A refund (RF) always comes out of one receipt** (`POST /billing/receipts/:id/refunds`, `billing:edit`, reason required, its own method and date) and names it in `invoice_payments.source_payment_id`. It can never exceed what the receipt still holds: the service checks under a row lock and the trigger `invoice_payments_refund_within_receipt` checks again, and the two allocation guards now subtract refunds taken out of a receipt (migration `20261020110000_receipts_refunds_vat`). Such refunds carry `refund_scope = 'credit'` (they touch no invoice). `POST /billing/invoices/:id/refunds` (refund straight off an invoice) still exists for API callers but no screen uses it and it reduces no receipt.

**Cancelling an invoice is not refunding.** `POST /billing/invoices/:id/void` now removes the invoice's allocations, so the money goes back to "open" on the receipts that paid it, still the patient's; with `refund: true` + `refund_method` it also hands that money back, one RF per receipt, in the same transaction. The response and the audit row list `released_receipts` and `refunds`, because the cancelled invoice no longer shows them. An invoice carrying an old-style invoice refund is refused (that money already left).

**VAT** is like the discount: 0% unless the user enters a rate when making the invoice (`vat_percent`, `vat_amount`). `subtotal - discount = taxable; taxable * vat% = vat_amount; total = taxable + vat_amount`, rounded once (`invoiceFigures`, the database constraint `treatment_invoices_discount_within_subtotal` checks the same). An issued invoice is frozen: to change its price, cancel and reissue.

**Expenses are supplier bills.** Each has its EX number, an optional supplier (`expense_suppliers`, remembered, unique name per clinic), the supplier's own bill number (`supplier_bill_number`, the "secondary ID"), the bill date (`expense_date`; the day money left is on each `expense_payments.payment_date`), an informational `vat_included`, the clinic's own categories (`expense_categories`: `expenses.category` stores a key that never changes; the six old categories are seeded, clinics add, rename and hide their own) and files (`expense_attachments`, Supabase Storage, `POST /expenses/:id/attachments`). Migration `20261020120000_expense_suppliers_categories_attachments`. Who recorded an expense or a payment is the session user; `created_by` in the body is ignored.

**Repeating expenses** (`expense_reminders`, migration `20261020130000_expense_reminders`): daily, weekly on a weekday, monthly or every 3 months on day 1-28 or the last day, yearly on a month and day; ends never, after N, or on a date; a fixed amount or "varies" (created at 0 to fill in). The schedule is pure and tested (`reminder-schedule.ts`). There is no scheduler: `GET /expenses` (the HTTP route, not the service, so the read-only AI assistant never writes) turns every due day up to the clinic's today into a PENDING expense, with the reminder row locked and the unique index `expenses_reminder_due_unique` as a backstop, so the same rent is never created twice. They wait in the Expenses page's **To pay** view until paid.

**Where money is entered (owner's rule):** only on the Billing, Payments and Expenses pages. Other pages may link there; none has a money form.

### Patient files, lab cases and outside doctors
**Phone numbers** everywhere go through `IsPhone()` (`src/shared/common/phone.ts`): digits with optional `+ ( ) -` and spaces, 6 to 20 digits, blank treated as not given, the typed form stored as typed. It guards every number the clinic keeps (patient, work, both emergency contacts, staff, labs, outside doctors, branches, the organization). Before it, the fields were `@IsString()` only and happily stored "abcdef".

**The patient file** (`patient_profiles`) reads like a real document: besides the medical fields it carries work (`occupation`, `employer`, `work_phone`), two emergency contacts with their relationship (`emergency_contact_relationship`, `emergency_contact_2_*`) and identity (`national_id`, `marital_status`, `nationality`, `preferred_language`; the last two are CHECK-constrained lists). `PatientsService.patientSelect` lists every column the screen shows, so **a new profile column must be added there too** or it saves and never comes back. Edited at `/admin/patients` → a patient → Edit, which sends profile fields to `PATCH /patients/:id` and name/phone/birth date to `PATCH /users/:id`, checking both answers.

**Lab cases** (`lab_orders`) carry what the technician needs: `material`, `units`, `tracking_ref`, `impression_method` (digital | physical), `try_in_at`, and remake tracking (`remake_of_id` → the order it replaces, with a required `remake_reason`; a remake must belong to the same patient and may not be itself). A lab (`dental_labs`) has `contact_person`, `turnaround_days`, `payment_terms` and `tax_number`; when an order is sent with no `due_at`, the due date defaults to the send date plus that lab's turnaround.

**Outside doctors**: `specialist_consultations.direction` records which way the patient moved — `referred_out` (we sent them to the outside doctor), `referred_in` (the outside doctor sent them to us) or `visiting` (the outside doctor treated the patient here). It decides who bills: on `referred_out` the other clinic charges the patient and `fee` is what was agreed with them; on `referred_in` and `visiting` the work happens here, so it is invoiced from the billing page as usual.

Migrations `20261016160000_patient_lab_specialist_detail` (columns, CHECKs, comments) and `20261016170000_agent_views_new_columns`. **A new column on a table the assistant may read must also be added to that table's view in schema `agent`**, or `agent-pricing-views.spec.ts` fails; `CREATE OR REPLACE VIEW` may only append columns, so new ones go at the end of the existing list. Neither app has a screen for labs or outside doctors yet: both are API-only (`/api/labs`, `/api/lab-orders`, `/api/specialists`, `/api/consultations`).

### Roles & permissions (`src/shared/authorization/`)
- `permissions.ts` is the catalog: every capability of the API as `<area>:<action>`, grouped for display, plus the default roles. The actions are CRUD: `read` to view, `create` to add, `edit` to change, `delete` to remove (`appointments:read`, `patients:create`, `records:edit`, `billing:delete`, …), so a role can be allowed to add work without being allowed to delete it. An area only carries the actions it has routes for (`documents` is never edited), and a few capabilities are not CRUD (`clinic:settings`, `pricing:read`, `agent:use`). The catalog is code because endpoints are code; add a permission there when you add a capability, then guard the route with `@RequirePermissions()` naming the action that route performs (`POST /invoices/:id/void` is a `billing:edit`, not a create). Migration `20261016120000_crud_permissions` is what split the old catch-all `:write` / `:manage` keys and carried every clinic's roles over.
- Which role holds which permission is per-clinic data: tables `roles` (`organization_id`, `key`, `name`, `is_system`) and `role_permissions`, both under RLS. `users.role` stores the role key. `RolesService.ensureDefaults()` seeds admin / doctor / secretary / patient for a new clinic (on creation and lazily on first use).
- `admin` always has every permission and `patient` none (both locked); doctor and secretary are editable; clinics can add custom roles. Deleting a role in use or a built-in role is refused.
- API: `GET /api/permissions`, `GET /api/roles` (need `staff:read`); `POST/PATCH/DELETE /api/roles[/:key]` (need `roles:create` / `roles:edit` / `roles:delete`); `/api/auth/me` returns the caller's `permissions` so the UI can hide what the role cannot do.
- UI: clinic admins manage this at `/admin/roles` (`client-app/frontend/app/admin/roles/`, API wrapper in `lib/api/roles.ts`). The admin UI mirrors the API: `lib/permissions.ts` (`usePermissions().can(key)`, from `/auth/me`) and `lib/adminAccess.ts` (screen → permission; read by `AdminScreenGuard` in the admin layout, the sidebar and the command palette) hide screens and write buttons the role lacks. When you add a route with `@RequirePermissions`, gate its button with `can(...)` too. The chart never bills, so `POST /patient-work[/complete]` needs only `records:*`; `billing:create` guards the billing page where invoices are made, and giving a plan to a patient.
- Tests: `permissions.guard.spec.ts`, `roles.service.spec.ts`, `access-control.service.spec.ts`; `scripts/smoke-tenancy.js` section 5 proves that editing a role changes what its holder can reach on the next request.
- **Every route is covered.** `route-inventory.ts` reads the decorators of every `*.controller.ts` and `route-coverage.spec.ts` fails when a route has neither `@Public`, `@Roles` nor `@RequirePermissions` and is not in its `SELF_SERVICE_ROUTES` list (routes that check ownership in the handler; each entry names the check). `npm run routes -- --table` prints the inventory. `npm run smoke:permissions` (`scripts/smoke-permissions.js`) then calls every route of the running API as no-token / patient / staff-with-no-permission / clinic admin / superadmin inside a throwaway clinic and checks each answer against the declared protection (`ROUTE_FILTER=users` limits it). Run it after touching any controller.

### AI assistant (`src/patient/agent/`)
The assistant is read-only (it lists, reports and queries; it never books, cancels, invoices or notifies) and acts with the caller's permissions, never its own. `agent-access.ts` labels every tool (`TOOL_PERMISSIONS`) and every table the SQL tool may read (`TABLE_PERMISSIONS`) with a key from the catalog; the model only receives the tools the user's role holds, and `tools/tool-runner.ts` re-checks before running (handlers live in `tools/<area>.tools.ts`, one file per area; `agent.service.ts` only talks to OpenAI). `query_database` is judged from its syntax tree (`sql-policy.ts`, pgsql-ast-parser): one read-only statement, `public` tables only, allowlisted functions, no CTE named after a real table; then `guarded-select.ts` runs it on the tenant connection in a READ ONLY transaction as the database role `dental_agent`, with the caller's permission keys in the transaction-local setting `app.agent_permissions`: every clinic table has a RESTRICTIVE policy for that role that raises unless the required key is present (migration `20261008210000_agent_permissions_rls`), so the database itself enforces clinic, branch and role permissions; patient rows of `users` additionally need `patients:read` (migration `20261008230000_agent_users_patient_rows`). Rows are capped and the transaction is rolled back if any `app.*` setting changed. Conversations live on the server, one row per user in `agent_conversations` (`conversation-store.ts`, migration `20261013210000_agent_conversations`): the client sends only the new message (`POST /agent/chat { message }`), reads its own history (`GET /agent/chat`) and forgets it (`DELETE /agent/chat`); the table has no grant for `dental_agent`, so no chat is reachable through SQL. Every answer also writes one `agent_usage` row (`usage-recorder.ts`, migration `20261013220000_agent_usage`: tokens in/out summed over the rounds, rounds, tool calls, duration; never the question text), which the platform console's **AI usage** page reads (`super-admin-app/backend/src/ai-usage`, `GET /ai-usage`, `/ai-usage/organizations/:id`, `/ai-usage/accounts/:userId`) to show spend per clinic, per account and per question; costs are estimates from the list prices in `ai-usage.service.ts`. Text filters are not a boundary here: add rules to the policy or the database, not to a regex. Tests: `agent-access.spec.ts`, `sql-policy.spec.ts`, `guarded-select.spec.ts`, `agent.service.spec.ts` (stubbed OpenAI); `npm run smoke:agent` replays every known bypass against the real database as the demo secretary. A new tool or table without a label fails `agent-access.spec.ts`; changing `TABLE_PERMISSIONS` without a matching migration fails `agent-permissions-migration.spec.ts`.

## Platform console (`super-admin-app/`)
A separate operator application on the same database: `super-admin-app/backend` (NestJS, :5100) and `super-admin-app/frontend` (Next.js, :3100, same design system and copied UI primitives). It onboards clinics (organization + default branch + clinic profile + first admin with a password setup link into the clinic app), monitors all clinics, suspends/reactivates them, manages platform admins (`superadmin` users with `organization_id NULL`), and manages every clinic's accounts, roles and permissions: `GET /accounts` (cross-clinic search), `GET|PATCH /organizations/:id/accounts[/:userId]`, `POST .../accounts/:userId/password-reset` (new set-password link, emailed when SMTP_* is configured), `GET /permissions`, `GET|POST|PATCH|DELETE /organizations/:id/roles[/:key]`. The rules are the clinic app's (admin locked, patient none, built-in and in-use roles undeletable, a clinic keeps one active admin); `src/catalog/permissions.ts` is a copy of the clinic catalog kept identical by `permissions.sync.spec.ts`. Every change is written to the clinic's `audit_logs` as `platform.*`. It has its own token (`PLATFORM_JWT_SECRET`, audience `platform`); clinic tokens are refused and vice versa. The Prisma client comes from the shared `client-app/backend/prisma/schema.prisma` via its second generator (`npm run prisma:generate` in `super-admin-app/backend`; keep `prisma` pinned to the clinic backend's version). Run both with `npm run dev:platform` from the repo root. Tests: `npm test` and `npm run smoke` in `super-admin-app/backend`; `npm run typecheck && npm run build` in `super-admin-app/frontend`. See `super-admin-app/README.md`.

## Key Conventions
- Use `class-validator` DTOs for all NestJS controller inputs
- Free-text `search` parameters go through `src/shared/common/text-search.ts` (`personSearchTiers` for first/last names, `textSearchTiers` for plain columns, run with `searchWithFallback`): the query loosens tier by tier (exact → all words → any word) and `meta.searchTier` tells the client and the AI assistant how loose the match was. Do not hand-roll `contains` filters for a new search.
- shadcn/ui components are in `components/ui/` — add new ones with `npx shadcn@latest add <component>`
- Path alias `@/*` maps to each frontend's own root (`client-app/frontend`, `super-admin-app/frontend`)
- Backend output dir is `client-app/backend/dist/`; never edit generated files in `client-app/backend/src/generated/`
